# Crew Health improvements for the challenge demo

The [challenge brief](./Challenge%20Description.docx) asks astronauts to gather indicators, assess their own health, and act. Use one fictional incident to demonstrate all three steps. The proposed demo target is for a first-time reviewer to record an action and recover the assigned follow-up in three minutes without coaching.

| Order | Change | Implementation | Acceptance check |
|---|---|---|---|
| 1 | Open a fictional mission from the dashboard | Add **Try a fictional mission** beside the profile controls. Open the existing import preview in `app.js` with the cached complete-workflow CSV selected. Show the synthetic destination and let the user confirm. Use the complete fixture for the incident because it includes events and assignments. Keep the clean device CSV as the ordinary device import example. | From a fresh profile, preview and confirm the sample, then find the fictional 14:12 incident. Cancel writes nothing. A second launch can return to the saved demo without losing the first action. |
| 2 | Make each reading understandable | In Latest readings, show the observation UTC time and a short status. Derive numeric status from the applicable rule, including the personal sleep reference. Use green for a value within that reference and amber for a crossing. Use neutral text for missing, faulty or unevaluable values. Display freshness separately when the rule defines it. Keep mood descriptive. In finding details, show the observation, its comparison, and the import or detection time when recorded. | A boundary value, a missing value, an older in-range value and a historical crossing each read differently without relying on color. A legacy record with unknown detection time displays that uncertainty. Compare units and displayed times against the source row. |
| 3 | Put the next assigned check on the dashboard | Add a compact **Next crew check** near the review summary. Reuse existing mission actions and personal tasks. Show the owner, full UTC deadline, and an action that opens the linked case. Prioritize overdue work, then the earliest deadline. Keep private support details within the requesting profile. | Record an action on the 14:12 case and assign a 14:30 check. Acknowledging the case leaves the check visible. | 5 | Rehearse the demo and verify it on the tablet | Update the judging walkthrough in the README to use the dashboard entry point. Run the repository suite and rehearse the incident on the target tablet. After provisioning, stop the local server, reopen the app, complete the check and inspect the Log. Rehearse once with a first-time user before claiming the three-minute target. |

## Five short demonstrations from existing fictional records

| Hazard | What the reviewer should be able to show |
|---|---|
| Radiation | Compare the partial walk log showing 16 µSv and 80 minutes missing with the completed log showing 24 µSv across 120 minutes. |
| Isolation | Compare five hours slept with five versus eight available. Show how the follow-up changes and that a crew member can request support independently. |
| Distance from Earth | Use the 14:12 incident as the main demo. Open the cached procedure, save the action, assign the 14:30 check and recover it offline. |
| Changing gravity | Correct the landing time from 09:00 to 09:10. Show the interval to dizziness onset changing from 20 to 10 minutes while the 09:45 assessment remains scheduled. |
| Closed habitat | Show an interval crossing in sleeping quarters, the overlapping symptom and the later import time. Contrast that evidence with a single CO₂ point reading from the device sample. |

Use the acceptance scenarios and fixture variants described in the [repository guide](./AGENTS.md). Build changes in the existing browser app and local rule modules. Run regression checks at each milestone and update the service-worker cache with changed assets. The first usable release includes milestones 1–3 and an offline rehearsal. Complete the guidance and five-hazard walkthrough before the judging presentation.
